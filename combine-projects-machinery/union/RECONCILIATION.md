# Machinery reconciliation: ferrislicer × dwc-ng

Row format: id | ferrislicer (concise, project terms) | dwc-ng (concise,
project terms) | proposed universal form (lay language) | your feedback.

- `—` = the project has no version of this behavior.
- `⚔` prefix on the universal cell = genuine conflict; ferrislicer's demand
  won; the dwc-ng column shows what was overruled. Your feedback decides.
- "dropped nuance:" inside a universal cell = fine print deliberately
  simplified away; say so in feedback if it must survive.
- Leave your verdict in the last column: blank/OK = approved as written;
  anything else = instruction for phase 3.

## 1. Straight Talk

*dwc-ng has no straight-talk section. Its honesty demands fire on verification
events (a diagnosis, a capability claim, a closed question) and are rowed in
group 3, not duplicated here.*

| id | ferrislicer | dwc-ng | proposed universal form | |
|---|---|---|---|---|
| 1.1 | "I don't know" said the moment it's true; never papered over with a plausible plan | — | Say "I don't know" the moment it is true. Not knowing is a reportable state, never hidden behind a confident-sounding plan. | |
| 1.2 | Every claim carries status: measured (command + output) or believed (labeled, plus what would verify it); "fixed"/"safe" with no evidence in the same message = violation | — | Every claim says whether it is measured or believed. | 1.3 | Attribution only after isolation: "X caused Y" requires the isolating bisect or toggle; otherwise "not yet isolated" | — | Name a cause only once you have run the thing that isolates it. Until then, say the cause is not yet isolated. Row 3.14 adds the sharper version for a diagnosis. | |
| 1.4 | Deviations announced BEFORE they happen, never discovered later; told-one-thing-done-another is the target failure | — | If what you are about to do differs from what was agreed, stop and say so first. Being told about it afterwards is the failure this rule exists to kill. | |

## 3. Verification & Evidence

*The gate-side instances of these rules — a gate printing its own denominator,
a merge gate not trusting parent order — fire when a gate runs and belong with
the gate rules, not here. Proving a change against a stand-in for the real
system is likewise its own group.*

| id | ferrislicer | dwc-ng | proposed universal form | |
|---|---|---|---|---|
| 3.1 | A change ships with its ASSUMPTIONS COMPILED — the beliefs that make the choice and the design legitimate | — | Every change writes down the beliefs that make its design and its choices legitimate. | |
| 3.2 | Expected BLAST RADIUS names both halves: what SHOULD change and what SHOULD NOT; the "should not" half carries the information | — | Every change predicts what it will affect and, just as explicitly, what it must leave alone. The second half is the one that can be proved wrong, so it is the half that carries the information. | |
| 3.3 | Written BEFORE the coding: assumptions compiled after the fact describe what happened, they are not a prediction that could have failed | — | Write the predictions before doing the work. Written afterwards they only describe what happened; they were never able to fail. | |
| 3.4 | Confirmed AFTER: each assumption and each expected truth named and reported HELD or DID NOT HOLD — never a blanket "tests pass" | — | After the work, confirm each prediction one by one and say for each whether it held. A blanket "everything passed" is not a confirmation. | |
| 3.5 | An unconfirmed expectation is an UNFINISHED change — not a caveat, not a follow-up ticket | — | A prediction left unconfirmed means the work is not finished. It is not a caveat and not a follow-up item. | |
| 3.6 | A violated expectation is a REPORTABLE RESULT at full strength; whether the change was wrong or the assumption was is an explicit finding | — | A prediction that fails is a result to report at full strength, not a mess to tidy. Say explicitly which was wrong: the work, or the belief behind it. | |
| 3.7 | The change DECLARES its output bar in advance — byte-identity for value-neutral work, structural parity plus invariants for deliberate algorithmic work; mislabelling a behaviour change as a refactor dodges the bar | — | A change declares in advance which standard it is claiming: identical output, because it was meant to change nothing, or structural checks, because it deliberately changes behaviour. Calling a behaviour change a cleanup is how that standard gets dodged. dropped nuance: which standard applies to which kind of work is a separate standing decision, not the author's to pick. | |
| 3.8 | A claim of byte-identical output must be measured by building and diffing, never assumed | — | A claim that output is unchanged is measured by producing the output and comparing it. It is never assumed. | |
| 3.9 | State what the measurement COULD see in the same breath as the claim; scope that differs from the claim is evidence for a DIFFERENT question that reads exactly like evidence for yours | Named as one generator: a check that can only speak to the instance in front of it was treated as proof of the class, premise or diagnosis it was attached to | Say what your check could actually see, in the same breath as the claim it supports. | 3.10 | Ask WHY the result looks like that, not WHETHER it does — every failed case was green, plausible, and answering a question nobody asked | — | Ask why the result looks the way it does, not merely whether it looks right. Green and plausible is what a wrong answer to an unasked question looks like. | |
| 3.11 | A subagent's confidence is not scope: an enumeration returned 21 rows at CERTAIN where the file held 22 — verify the COUNT independently | — | Someone else's confidence is not evidence of coverage. Verify counts yourself, because a complete-looking list is not proof of completeness. | |
| 3.12 | A clean check does not shorten the list: required checks enumerated BEFORE the first one runs; a pass on one never cancels another. A good result is the most dangerous place to stop, because stopping then feels earned. | |
| 3.13 | — | A finding or ruling using a class noun ("class", "shape", "pattern") must search the changed layer and fix or defer every hit BY NAME before the task closes | If you call a defect a class, a shape, or a pattern, you owe every instance of it: search the area you changed and fix or defer each one by name before closing. | 3.15 | — | A fix for a falsified premise states what the broken premise assumed about its INPUTS and checks whether the replacement inherits it one layer down | When the task exists because an earlier belief was proved false, say what that belief assumed about its inputs, and check whether the replacement quietly assumes the same thing one layer down. | |
| 3.16 | — | Closing an open question requires naming the variable whose value would flip the answer, as something a later reader could check and find FALSE; only prose means it is a guess with a due date | A question is closed only when you can name what would have to be true, in a form a later reader can check and find false. | 3.17 | — | Before any action leaving the working tree, verify the target from the environment, not from a document: the tracker's remote, the configured host, the branch | Before doing anything that reaches outside your own working copy, get the target from the environment itself, not from a document. | 3.18 | — | Before claiming a hook, test, gate, flag, script or harness exists or would catch something, run the check that could FALSIFY it; this repo's own prose is the most dangerous source, because it reads authoritative and goes stale silently | Before claiming that some piece of tooling exists, blocks something, or would catch a given fault, run the check that could prove you wrong. | 3.19 | — | These rules fire on an ARTEFACT: when you write the word, the check is due | The trigger is the word you just wrote. Writing "class", "confirmed", "closed", or naming what the tooling can do is what makes the matching check due. | |
| 3.20 | TDD: a failing test written first and verified red, then the minimal implementation to go green | — | Write the failing test first and watch it fail, then write the smallest code that makes it pass. | |
| 3.21 | Every bug fix, feature, function, class and method ships with a unit test, a fixture generator, and coverage in every related integration test | — | Every fix and every new unit of code ships with its own test, something that generates its test data, and a case added to each broader test that covers it. | |

## 4. Agent Topology & Economy

*The worktree lifecycle rules — one per campaign, merge when green, delete
branch and worktree — belong with the worktree group; only the dispatch-time
demands are rowed here. Read-only constraints on reviewing agents are a
separate group.*

| id | ferrislicer | dwc-ng | proposed universal form | |
|---|---|---|---|---|
| 4.1 | Efforts START in agents: the main loop's own work is design, adjudication, verdicts and verifying a returned result; everything else is dispatched | The main agent does no work: it holds conversation, adjudication and relay, and delegates everything else | Work is dispatched to a subordinate agent by default. The main conversation keeps only design, adjudication, verdicts, relaying, and checking what comes back. | |
| 4.2 | NO size threshold decides this; a proposed threshold was raised and rejected | The line is intent, not file count: reading a file to ANSWER a question is conversation, reading it to CHANGE it is work | Size never decides whether to dispatch. | 4.3 | The cost conserved is main-loop CONTEXT, not model spend — tool output an agent absorbs and returns as a summary | Identical wording and identical reason | What this conserves is the main conversation's own attention, not money. | 4.4 | Loading a skill's full body into main-loop context to do the work yourself IS doing the work; the skill invocation goes inside the dispatched agent's prompt | — | Pulling a procedure's full text into the main conversation to follow it yourself is doing the work. | 4.5 | Cheapest capable model per subagent task; quality held by verification gates, never by model tier | — | Use the cheapest model that can do each dispatched task. Quality is held by the checks on the result, never by paying for a bigger model. | |
| 4.6 | A cheap agent whose spot-check fails gets its batch redone one tier up — recorded, never silent | — | When a cheap agent's work fails its spot-check, redo that batch one tier up and record that you did. Never re-run it silently. | |
